# Phase 6B.2 — pinned BigEarthNet.txt source audit

## Verified source and retrieval

The source is the **author-maintained official** [`BIFOLD-BigEarthNetv2-0/BigEarthNet.txt`](https://huggingface.co/datasets/BIFOLD-BigEarthNetv2-0/BigEarthNet.txt) distribution, pinned to commit `72d865f2146f0a85b720f7f3ca1cdbaeafc3d316`. File: `BigEarthNet.txt.parquet`; [pinned download URL](https://huggingface.co/datasets/BIFOLD-BigEarthNetv2-0/BigEarthNet.txt/resolve/72d865f2146f0a85b720f7f3ca1cdbaeafc3d316/BigEarthNet.txt.parquet). It was downloaded via `huggingface_hub.hf_hub_download` on 2026-09-15 UTC into ignored `data/raw/bigearthnet_txt/source/`, without imagery. Actual local size: **466,819,745 bytes**; independently computed SHA-256: `d3b97f999456016bb13c2a8e94b8f47825654f07a0394a6b266a38b750ca1554`. This equals both the pinned publisher file metadata and Ravi's pinned matcher constant. No mirror was used. Publisher card, loader and Ravi's current matcher/downloader/receipts were inspected at their pinned commits; neither repository was copied into SatQuery.

The Parquet footer and full scan both report **9,553,962 rows**, 78 row groups, and 13 fields: `ID` (int64), `s1_name`, `patch_id`, `input`, `output`, `type`, `category`, `split` (UTF-8 strings), `latitude`, `longitude` (float64), and `country`, `season`, `climate_zone` (UTF-8 strings). Parquet has no text delimiter or header row. The scan found zero null fields and zero rows missing/empty in the required matching/text/type/split fields. Publisher `type` counts actually observed: binary 3,625,160; MCQ 3,259,184; bounding box 2,205,686; captioning 463,932. Source partitions actually observed: train 4,674,281; validation 2,454,690; test 2,409,962; manually checked `bench` 15,029. Full type/category counts and types are in `source_schema.json`.

## Verified identifiers and real selection

Source `patch_id` is the **full** Sentinel-2 v2 patch ID (for example `S2A_MSIL2A_20170613T101031_N9999_R022_T33UUP_26_57`), exactly the canonical `area_id` syntax. It includes processing/acquisition metadata and the tile/patch suffix. Source `s1_name` is the independent Sentinel-1 name (for example `S1B_IW_GRDH_1SDV_20170612T165809_33UUP_26_57`). Our manifest also has a shorter `s2_identity`, so matching uses the full `area_id` together with `s1_identity`; no substring, order or filename fallback is used. Identifier case and separators were compared literally. Ravi's matcher uses the same two source fields against its own distinct 1,000-image metadata set and quarantines an image when any of its rows are `bench` or conflict with the image split. We adapted that image-level holdout rule, not Ravi's Parquet output/experimental architecture.

The full source scan found **101,571 rows** whose `patch_id` belongs to our frozen 5,000-area inventory. Every selected row matched the associated `s1_name` exactly: exact 101,571; partial 0; conflicting identity 0; unmatched within selected optical inventory 0; ambiguous 0 (duplicate manifest keys are rejected). The other 9,452,391 rows belong to images outside this experiment and are counted separately, not called failed matches. Actual matched images: 4,771. Selected images without any source row: 229; absence is not a negative label. Ravi's historical 20,453 rows/955 images refer to its 1,000-image subset and are **not** the result for our 5,000-image selection.

Actual selected task counts: binary Q&A **37,518**, MCQ **33,979**, captions **4,771**, text-reference boxes **12,179**, and point-guided boxes **13,124**. The publisher stores MCQ options inside `input` text (ordered `a)` through `d)` in inspected samples) and the reference answer as a letter in `output`; there is no separate options column. Binary sample answers are `yes`/`no`; captions are full-scene prose in `output`. Text-guided instructions contain `<ref>…</ref>`; point-guided instructions contain `<point>(…, …)</point>`. The derived `referenced_text`, `box`, and `point` fields keep `raw_source` fully intact. No class names or negative labels are inferred. These observed examples support the mapping already introduced in `annotation_schema_v1`; no breaking schema version or Pipeline 3 contract change was needed.

## Spatial representation and geometry

Publisher box answers are strings of the form `[first first, second second]`; point instructions contain `<point>(first, second)</point>`. All **25,303** selected box strings parse into four finite values between 0 and 1 with increasing first-to-third and second-to-fourth extents. All **13,124** point rows parse into two finite values between 0 and 1, and each point lies inside its paired box in corresponding positional coordinates. Of those, 690 instructions repeat the **same** point tag in concatenated wording; the repeated values agree, so they are parsed once while original text remains untouched. Geometry issue counts are zero. The observed numeric range and paired consistency justify labeling these as **source unit-square coordinates** for numeric validation. The publisher card and loader do **not** establish axis origin, exact x/y semantic ordering, inclusive/exclusive boundaries, pixel dimensions, S1-versus-S2 raster grid, or CRS transformation for the box/point strings. Those remain **UNKNOWN**. The separate `latitude`/`longitude` fields describe patch centers and are not treated as box coordinates. No coordinate transform, clamp or grounding target export is implemented.

## Splits, quarantine and leakage

Every record inherits its matched image's frozen 4,600/200/200 experiment split. Counts by inherited split: train **93,208**, validation **4,175**, test **4,188**, on 4,385/197/189 images respectively. Source partitions among selected rows agree with the image split except one test image with **29** publisher `bench` rows. The whole image is assigned `bench_holdout`, so the effective/use partitions are train **93,208**, validation **4,175**, test **4,159**, benchmark holdout **29**; underlying image counts are 4,385/197/188/1. Exactly **29** records are quarantined and 101,542 validate. No image was split at annotation level. No training export exists, and test/bench rows assigned to train are zero.

Within the selected inventory, duplicate annotation IDs, identical raw rows, conflicting source IDs, duplicate image/question combinations, image identity overlap across splits and test-to-train assignments are all **zero**. There are **2,001** identical question/answer strings occurring across different images in different splits. Generic repeated wording/answers are not image or source-record leakage; these repetitions are reported, not automatically quarantined. The source contains MCQ tasks about country (4,770 rows), season (4,771) and climate zone (4,770) alongside those same metadata fields, so metadata-to-answer exposure is a **real risk for a later training/evaluation design**. Acquisition dates/tile information encoded in image IDs may also reveal geography/season; task-specific filename leakage was not proven absent. Reference-box reuse is outside this phase because no learned grounding/export exists. The audit therefore does not claim complete leakage absence.
